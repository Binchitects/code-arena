# Measurements for 0.4

Built with `--release` in the build image on the build host (Linux x64, 24 cores); each figure the median of 20 runs
(30 for `version`).

| what | 0.3 | 0.4 | the plan's target |
|---|---|---|---|
| the static Linux binary (x64, musl) | 11.1 MB | 12.6 MB | |
| `code-arena version` (settings, the connection and the edition read) | 1.9 ms | 1.9 ms | |
| the session store, 10,000 messages: append a message, on disk | 0.40 ms | 0.23 ms | |
| open the store and read the last 30 turns | 0.60 ms | 0.73 ms | ≤ 30 ms |
| read the 30 turns before those | 0.33 ms | 0.36 ms | |
| what the model reads (from the last compaction) | 0.71 ms | 0.82 ms | |
| search the folder's sessions (FTS5) | 3.57 ms | 4.53 ms | |

The store's schema 4 (the session a fork came from) costs nothing measurable; the differences are the host's load on
the day. `cargo run --release -p ca-session --example measure` gives them.

The binary grew with hooks, sub-agents, goals, model-made commits, steps in worktrees, loops and schedules, plugins,
Arena's agents and scheduled tasks, forks, output styles and the status line, and the refusals' reader (regex).

## On a real Arena (8.2.2, the build host's own deploy), 2026-11-26

- `doctor`: every feature answers, `automation.*` included.
- `code-arena agents` lists the person's three agents (all off); `code-arena tasks` says there are none. Nothing was
  run there.
- Not measured: the cache across runs. The engine was failing to load its models that day ("failed to load", or an
  empty 500). Code Arena's own requests have the same system prompt, tools and parameters from one run to the next.
